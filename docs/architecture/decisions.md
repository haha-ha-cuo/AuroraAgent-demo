# 关键决策记录（ADR）

> 记录影响架构走向的关键决策、背景与待办。新增决策请沿用 ADR 编号并标注状态（已采纳 / 待定）。

## ADR-001：能力特化层与缓存解耦 {: #adr-001 }

- **状态**：已采纳
- **背景**：早期构想以 “KV Cache 层” 同时承载「能力特化」与「缓存」，但 “KV Cache” 在 LLM 语境中通常指推理时的注意力 key-value 缓存，容易混淆。
- **决策**：拆分为两个独立概念——**能力特化层**（用户可插拔的上下文、工具、提示、检索策略）与**缓存层**（prompt / 结果复用，纯内部优化）。
- **影响**：对外接口面向能力特化层；缓存作为独立优化模块单独设计。
- **文档**：[能力特化层](capability-layer.md)

## ADR-002：模型接入 = 远程 API + 本地 API 管理 {: #adr-002 }

- **状态**：已采纳
- **背景**：桌面本地化若走本地推理（Ollama / llama.cpp），打包体积、硬件适配、三平台维护成本高。
- **决策**：模型统一走**远程 API**，应用内提供**本地 API 管理层**负责密钥、端点与客户端构建；密钥不进入 Agent 上下文、不落日志；离线演示需显式选择 **mock 模式**，OpenAI 模式配置错误不得静默回退。
- **影响**：跨平台一致、可切换供应商；需妥善处理密钥安全。
- **文档**：[模型接入与本地 API 管理](model-access.md)

## ADR-003：直接用 langchain-core + langgraph {: #adr-003 }

- **状态**：已采纳
- **背景**：`langchain` 元包偏旧、体积大，现代组合是 `langchain-core`（核心抽象）+ `langgraph`（编排）+ 各集成包（如 `langchain-openai`）。
- **决策**：不引入 `langchain` 元包，直接依赖 `langchain-core`、`langgraph` 与所需的集成包。
- **影响**：更可控的依赖面与升级成本；文档与代码统一使用新拆分。

## ADR-004：委派树的失败传播与资源上限（待定） {: #adr-004 }

- **状态**：待定
- **背景**：树形委派需要明确失败语义与资源边界，否则会出现无限递归与成本失控。
- **开发实现**：AuroraHarness 已落地计划整体校验、深度/单计划/整轮任务上限、逐层失败与局部重试；详见[执行校验与资源限制](execution-runtime.md)。完整的 token、成本、时长与依赖策略仍待定。
- **待决策项**：
  - 叶子失败在哪个层级触发父节点重规划；
  - 子树局部重试的状态保存与次数上限；
  - 树深 / 扇出 / 总预算（token、成本、时长）上限；
  - 评审（review）节点的触发条件与通过标准。

## ADR-005：安全权限模型（阶段二一级设计项） {: #adr-005 }

- **状态**：已采纳（确认门已落地最小实现，其余待定）
- **背景**：能读文件、跑 shell、改代码的 Agent 本质是本机 RCE 入口，且用户代码库本身可能被提示注入。
- **已落地**：
  - 确认门（`demo_agent/gate.py`）：工具按风险分级 read / write / execute，写与执行默认拒绝，需确认才放行；`--yes` 全放行、交互终端逐条确认、非交互默认拒绝。
  - 敏感文件守卫：`list_files` / `read_file` / `write_file` 拒绝 `.env`、密钥文件。
- **待决策项**：
  - 命令执行工具的白名单与 dry-run；
  - 文件系统沙箱（seatbelt / 容器）；
  - MCP Server 的供应链与权限边界；
  - 注入上下文（能力特化层）的防提示注入策略。

## ADR-006：评估与校准 {: #adr-006 }

**已采纳。** 用确定性基准检验任务识别、强度分档与工具执行，用单独启用的模型对照实验比较回答质量与 token 用量。

早期 demo 在当时的任务和模型上观察到由低档升至中档的收益。继续提高上限或让模型自由自评，收益并不稳定。由此保留 high 档的单遍生成，将质量核对放到可验证的材料与测试上。

AuroraHarness 开发版提供 14 项离线基准和两项文本对照任务。当前回归使用注入模型核对实际请求策略、盲评与报告。比较指定供应商时应另行运行 `aurora eval --live`，结合重复试验与人工抽检解释质量差异。[命令与统计口径](eval.md)

## ADR-007：桌面壳选型 = Tauri 2 + Nuxt(Vue3+TS) SPA {: #adr-007 }

- **状态**：已采纳
- **背景**：阶段三 MVP 曾以 Electron（+React）验证桌面壳与 Python 运行时的通信闭环；但进入「全平台分发」阶段，Electron 打包体积大、内存占用高、webview 内默认暴露 Node 运行时，攻击面更大，需重新评估壳框架。
- **决策**：
  - 桌面壳改用 **Tauri 2**：Rust 核心做系统胶水（sidecar 进程监督、钥匙串、更新器、单实例），前端运行在系统 webview（WKWebView / WebView2 / WebKitGTK）。
  - 前端改用 **Nuxt（Vue 3 + TypeScript）**，运行在 **SPA 模式（`ssr: false`）**：桌面场景无 SSR/Nitro 服务端需求，只取 Nuxt 的开发体验（文件路由、自动导入、模块生态）。
  - Python Agent 运行时保持独立，以 **sidecar 进程**随应用打包分发，由 Rust 负责拉起与监督；进程间通信走 **stdio（NDJSON 中继，经 Rust 转发）**，运行时**不监听任何本地端口**。
  - sidecar 打包采用 **python-build-standalone + uv**：独立可重定位 CPython + `uv pip install` 装好的站点包，作为资源目录随包分发、薄启动器拉起，不依赖系统 Python，并规避 PyInstaller 对 pydantic / langchain 动态导入的冻结风险。
- **影响**：
  - 仓库新增 Rust（Tauri core）与 Nuxt/Vue3+TS 两条技术线；Rust 保持薄壳，不承载业务逻辑，并承担 stdio 中继。
  - 通信走 stdio 中继后，运行时无任何网络监听面，攻击面进一步收窄。
  - 密钥管理上移到 Rust 侧系统钥匙串，仅以环境变量注入 sidecar，webview 不持有明文（强化 [ADR-002](#adr-002)）。
  - Tauri 能力权限系统与确认门（[ADR-005](#adr-005)）协同，形成「webview 最小权限 + 运行时风险分级」双重防线。
- **文档**：[桌面应用架构](desktop.md)
